# @tacit-ats/web

Next.js (App Router): the client area, where members of a client org sign in and work on their own jobs and pipeline.

Where members of a client org sign in and work: Phase 1 of tacit-internal's `docs/superpowers/specs/2026-10-13-ats-parity-design.md`. Dormant until configured: `/client/**` answers 404 unless `WORKOS_CLIENT_ID`, `WORKOS_API_KEY`, `WORKOS_COOKIE_PASSWORD` (32+ characters), `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are all set (`lib/client/config.ts`; the one-time WorkOS and Supabase steps are in this repo's `.env.example`).

- **One session, under one prefix** (`proxy.ts`, which matches only `/client` and `/client/**`; `/` redirects to `/client`). Clients sign in with WorkOS AuthKit (`wos-session`). Until 2026-10-14 this area lived inside tacit-internal's `apps/internal`, split by path from the staff session; it moved here so the client product and Tacit's workspace no longer share an app, a domain or a session.
- **`lib/client/session.ts`**: `resolveClient()` builds a per-request database client from the user's own WorkOS access token (`createUserClient`, role `authenticated`) and asks the database who that is (`current_actor_id()`), so the page and the policies agree by construction. Not bound yet means a first sign-in: `lib/client/bind.ts` matches the verified email to the actor an admin invited, inside the token's org (`@tacit-ats/core`'s `bindClientActor`). Nobody is created on sign-in. `requireClient()` is the throwing form, for actions.
- **Sign-ins that start at WorkOS.** Accepting a WorkOS invitation (or signing up from its email) runs AuthKit's hosted flow and then lands on `/client/callback` without the PKCE cookie our own sign-in sets, so AuthKit cannot verify it and refuses (`CallbackError` `missing_pkce_cookie` / `missing_auth_params` / `oauth_state_mismatch`). The account exists by then; the callback's `onError` (`lib/client/callback-error.ts`) answers with a "Your account is ready, continue" page linking to `/client`, which signs in from our side. Any other failure is a plain "Couldn't sign in, try again" page, never the error itself. A link, not a redirect, so a browser that drops the cookie cannot loop. (Until 2026-10-14 this was AuthKit's bare JSON error, the first thing an invited client saw.)
- **`lib/client/bind.ts` is the only file in the client area that may touch the service role**, and it returns a verdict, never the client.
- **`src/client-area.test.ts`** enforces the rules above from the source: the import walk (nothing reachable from `app/client` or `lib/client` may name a privileged client, except `lib/client/bind.ts`), and that every server action starts with `await requireClient()`.
- **Pages so far**: `/client` (Home: the Recruiting Overview below for admins and the hiring team; for a limited interviewer, the page it always was: the people they interview, the jobs they can see, the team), `/client/jobs` (Job Postings since 2026-10-29, below) and `/client/jobs/[id]` (2026-10-13: the job and its pipeline on the shared `components/pipeline-board.tsx`, plus "Add a candidate"). Everything is read through RLS; nothing is filtered in the page. A refused sign-in renders `app/client/refusal.tsx` on every page.
- **The job board** reads with core's `getRolePipeline` on the member's own client, so the cards are exactly the applications they may read (an external recruiter sees only their own adds; an interviewer gets a pointer to `/client` instead of a board). The edit controls appear only when `can_on_role(job, 'can_edit_pipeline')` says so, and "Add a candidate" also needs `can_add_people()`. The writes (`jobs/[id]/actions.ts`: add, move, edit stage/owner/next action, log a touch, remove) are core's pipeline functions on the same client, so the policies decide again. Adding goes through core's `addCandidateToRole`: an email already on a person the member can see reuses that person, otherwise a people row is made in the org; a person in the org the member cannot see is not revealed, so they get a second row. The action checks `can_edit_pipeline` before creating anyone, so a refused add leaves no orphan person. Notices and errors are codes (`jobs/messages.ts`). Core never touches the Tacit funnel for a client org's application (`advancePersonFunnel` returns for any org but Tacit's), and `getRolePipeline`'s `companyName` is empty for a member who may not read `companies` (everyone but an admin). A card's name opens the candidate page (`/client/candidates/[id]`). Its header links the job's post (`/client/jobs/[id]/post`).
- **Where a client org starts**: tacit-internal's ATS Admin (`/admin/orgs` in its `apps/internal`, staff admins only), with `@tacit/core`'s `createClientOrg` and `inviteOrgMember` on the service role. Nothing in this repo creates an org or its first admin; a first sign-in here only binds the actor that page invited.
- **`/client/team`** (2026-10-14): the org's members for everyone; an admin also sees who is invited and not signed in yet, and invites, re-sends and withdraws (`team/actions.ts`, codes in `team/messages.ts`). No service role: the actor is written by the `invite_org_member` definer function on the admin's own token (tacit-internal's packages/db, `20261014120000_client_invites`), which checks the caller is an admin and writes only into the org on that token, so the form never names an org. WorkOS then sends the email (`lib/client/workos.ts`, AuthKit's own `getWorkOS()` client, with the inviter named), and a first invitation WorkOS refuses is withdrawn again. Withdrawing deletes the unbound actor and revokes WorkOS's pending invitation for the address, best-effort: an accepted email with no actor behind it binds nobody. `@tacit-ats/core`'s `client-auth/invite.ts` holds the sequence. `ClientContext` now carries the token's WorkOS organization and user ids for this.
- **`/client/pipeline`** (2026-10-29; design/tats's Pipeline, the sidebar's **Routing & Tracking**): every open job's live applications on one read-only board. `lib/client/pipeline.ts`'s `readPipeline` reads on the member's own token: each open job through core's `getRolePipeline` (not `listOpenPipelines`, which reads `companies(name)`, admin-only for a client member, and fails for everyone else), and the non-cancelled `interviews` of the `interviewing` applications (150 ids a read). The columns are **computed, not stored** (`lib/client/pipeline-columns.ts`, pure, unit-tested): New (sourced, contacted), Screening, Scheduling (interviewing, nothing booked or held), Interview booked (a scheduled interview not yet ended), Your call (interviews held, a `scheduled` one past its end counting as held, nothing booked next), Offer; hired / rejected / withdrawn are left off. Job tabs (`?job=`), a name filter (`?q=`, a GET form), a dozen cards a column until "Show all" (`?all=<column>`). A card is the person, the job (the headline once one job is picked), one status line (relative times only, "Interview in 2d", so no time zone is needed) red when core calls it stalled, and the owner; it opens the candidate page, where the edit controls are (and on the job's board). An interviewer gets the same pointer home as on a job page. `pipeline.integration.test.ts` runs the read against the local stack: an admin's columns, a hiring manager seeing only their job (and its interviews), another company never.
- **`/client/jobs`, Job Postings** (2026-10-29; design/tats's `#jobs`, the sidebar's **Job Postings** in **Top of Funnel**): the careers page as applicants see it, "Careers at <org>", every job the member can see, a folding band per department (a `<details>`, no script). `lib/client/postings.ts`'s `readPostings` reads on the member's own token: `roles` directly (as `list_jobs` does, but with `department_id` and no cap of 50), `@tacit-ats/core`'s `clientTools.listDepartments` (archived ones too, for their paths) and `clientTools.listJobPosts` (asked again per job for the jobs missing when it stops at `LIST_MAX`). `lib/client/posting-groups.ts` (pure, unit-tested): each job's lead post (live, then draft, then closed; newest first), the departments in path order with empty ones left out, jobs in none (or one the member cannot read) last under **Other**; within a band open jobs first, then pending approval, paused, filled, closed, by title; a row's pill (Live is green only while `accepting`, the public page taking applications; Draft, Closed, No post) and a "Job paused" / "Job closed" pill when the job is not open. A row is the title and location, how many applied through its posts (counted under the answers policy) and are in its pipeline, the public link with a copy button while it takes applications (`/jobs/<slug>`, this app's own public page; the absolute URL from the request's host, `jobs/origin.ts`), and **Board** (`/client/jobs/[id]`); the row opens the posting. An interviewer gets the jobs they can see in one list, as before: no departments, no counts. **`/client/jobs/[id]/post`**: one job's post laid out like design/tats's posting editor, read-only: the sheet with the facts (location, department path, the job's status, published / closed day, applied) beside Overview (the description as plain text) and Application (`?tab=application`: each question drawn as the applicant sees it, with its type and whether it is required, then the self-identification line); `?post=` picks another of the job's posts (tabs when it has more than one); a job the member cannot see is a 404. **No editing yet**: `createJobPost`, `updateJobPost` and `setJobPostStatus` audit through `client_claim_write`, whose `p_source` takes only `claude`, `chatgpt` and `cli`, and the web app is none of them. Unlocking it: tacit-internal adds a web source to `client_claim_write` (`audit_log.source`'s check already allows `dashboard`), then `pnpm sync:tacit` and widen `ClientToolCtx["source"]` in core; until then the pages point to the client connector's `create_job_post` / `update_job_post` / `set_job_post_status`. `postings.integration.test.ts`: an admin's bands, counts and post states, a hiring manager's one job, an interviewer's ungrouped list without counts, another company never.
- **`/client/applicants`** (2026-10-29; design/tats's Applicant Tickets, `#triage`, under Job Postings in **Top of Funnel**): new job-board applicants read like email, in `ListReader`. `lib/client/applicants.ts`'s `readApplicantQueue` is `@tacit-ats/core`'s `clientTools.listApplicationsInbox` on the member's own token (source `job_board`, still at the first stage, with their answers, at most 50); `lib/client/applicant-queue.ts` (pure, unit-tested) groups it by job, newest first, picks `?a=<application id>` and splits the answers. The reader is the whole application as one document: name, email and phone, the job, every other answer as plain text (resume and LinkedIn are links only when `safeHref` reads an http(s) URL), and the source (the post). Under it the routing bar, shown only when `can_on_role(job, 'can_edit_pipeline')`: Interview (`interviewing`), Move to screening (`screening`), Decline (`rejected`, needing one of the org's unarchived `rejected` reasons). `applicants/actions.ts` runs `routeApplicant`, core's `moveStage` on the same client from the stage the queue showed (so a ticket someone else routed is not moved twice), then opens the next ticket; codes in `applicants/messages.ts`. - **`/client/interviews`** (2026-10-29; design/tats's Interviews, under Pipeline in **Routing & Tracking**): a `ListReader`, every interview the member can see but cancelled ones, newest 500. `lib/client/interviews.ts` reads on the member's own token: `interviews` directly (the policy gives an interviewer their own and everyone else the ones whose application they can read), the applications behind them for candidate and job, and core's `listMyInterviews` (`my_interviews()`) for the ones the member sits on without reading the application, which is all of them for an interviewer (`limited`), whose token cannot read applications. **Groups are computed** (`lib/client/interview-groups.ts`, pure, unit-tested): Upcoming (scheduled, not yet ended), then the past ones by a **verdict** from the `interview_feedback` recommendations the member may read: all yes / strong_yes is Pass, all no / strong_no Fail, both Mixed, none Read pending. A row the member cannot read feedback on stays Read pending, so the groups follow the org's `feedback_visibility` (`can_see_feedback`: an interviewer only ever reads their own; others per `after_submit` / `always` / `never`, admins always). `?i=<interview id>` selects; nothing picked shows the first beside the list (on a phone, the list alone). The reader: the candidate's loop from core's `getInterviewPlan` (`lib/client/interview-loop.ts`, pure, unit-tested: the plan's steps, then off-plan interviews by date, each with who ran it and Filed / Not filed / Not visible to you, never what; this round highlighted, later ones faded, other listed rounds linking to theirs), then this interview's feedback from core's `getFeedback` (recommendation, rating, scorecard ratings, notes as plain text) with a line when some of it is hidden from the member. Relative times only, as the Pipeline board. Read-only: no "reviewed" check (the prototype's was local state, there is no field), and no Granola notes or transcript (reading them needs the service role through apps/mcp's `client/granola.ts`, which the client area may not import). `interviews.integration.test.ts`: an admin, a hiring manager on one job (feedback held back under `after_submit` while their own interview is outstanding, shown under `always`), an interviewer seeing only their own interviews and their own feedback, and another company never.
- **`/client/schedule`** (2026-10-29; design/tats's Calendar, `#calendar`, under Interviews in **Routing & Tracking**; not `/client/calendar`, which is the Google Calendar connect redirect): every interview the member can see but cancelled ones, read-only, as a day or week grid or the month as a list (`?view=day|week|list`, `?date=YYYY-MM-DD`; keys D / W / L, ← / →, `.` for today). `lib/client/schedule.ts`'s `readSchedule` reads the way the Interviews page does, on the member's own token: `interviews` overlapping a window (at most 1,000, with a notice past that), the applications behind them, core's `listMyInterviews` (`my_interviews()`) for the ones the member sits on without reading the application (all of an interviewer's), each job's `department_id` (readable on every job the member can see, an interviewer's too) and, above interviewer, core's `listDepartments` for the names. **Time zones**: the server never lays out a clock time. `readWindow` (in `lib/client/schedule-layout.ts`, pure, unit-tested) reads a UTC window wide enough for any zone (the view's days, 14 hours before to 12 after; with no `?date=`, around the server's UTC date and a day either side), and `schedule/view.tsx`, a client component, places the interviews in the browser's zone (`Intl`'s `resolvedOptions().timeZone`, through `useSyncExternalStore` with a null server snapshot, so the server render and first paint draw the frame with no times rather than UTC ones); "today" is the browser's. The layout module places a day's interviews (clipped at midnight, side-by-side lanes counted per cluster of overlaps), widens the 8-19 grid to fit, groups the list by local day, and colours by department: the outermost department, the outermost ones taking design/tats's `--ev-*` tones in name order, grey for none, a steady tone by id for a department the member cannot read. An event shows the candidate, step, job, interviewers and location (a link only when `safeHref` reads http(s)) and opens `/client/interviews?i=<id>`. Left out: drag to create or move, "Find a time", holds, and the popover's move and cancel (moving a Google event from the web needs the calendar grants that only apps/mcp's `client/calendar.ts` may use). `schedule.integration.test.ts`: an admin (with department names), a hiring manager on one job, an interviewer seeing only theirs, cancelled ones never, another company never.
- **`/client/interviewers`** (2026-10-29; design/tats's Interviewers, `#bots~people`, under Interviews in **Routing & Tracking**): one row per member who interviews, read-only, counts only. `lib/client/interviewers.ts`'s `readInterviewers` reads on the member's own token: `interviews` (not cancelled, application not merged, `applications!inner` so a hiring manager counts only the interviews on applications they can read) from 30 days back to the end of next week, `hiring_team`, `roles` (title, status, department), `departments` (readable by the hiring team and admins), `org_members` for names, and `@tacit-ats/core`'s `clientTools.interviewerActivity` for the last 30 days. **Who is a row and the counts are computed** (`lib/client/interviewer-load.ts`, pure, unit-tested): an `interviewer` seat on a job not filled or closed, an interview in the window, or a row in the feedback report; interviews starting this calendar week (Monday to Sunday, **UTC**: an org has no time zone yet), next week, and in the 30 days before now; their jobs are their live hiring-team seats (any seat) plus the jobs of the interviews counted. **Grouped by department** where it can be derived: members have none, so it is the departments of their jobs (with parents, "Engineering > Platform"), one section each, then "Several departments", then "No department"; when no job has one (or the member reads none), one list. An interviewer gets the pointer home (`readInterviewers` itself refuses `limited`). Those actors are never offered as invitations to re-send (`org_pending_invites` skips them).
- **`/client/docs`** (2026-10-14): the client connector's docs, linked from the sidebar as "Documentation", behind the same `resolveClient()` gate as the other client pages. The pages are data in `lib/docs/client-pages.ts`, rendered by `components/docs/docs-view.tsx` (react-markdown + remark-gfm) with a ⌘K search. `lib/docs/docs.test.ts` reads `apps/mcp/src/client/server.ts` and fails when the tool reference lists a tool that is not registered or misses one that is: **add a row to the reference page when you add a tool.** tacit-internal's staff `/docs` shows a copy of these pages (its `lib/docs/client-pages.ts`); this file is the source, so tell that repo when it changes. `CLIENT_CONNECTOR_URL` is `https://ats-mcp.tacitawareness.com/api/client`, the mcp app's production domain: it must equal that project's `CLIENT_MCP_RESOURCE_URL`, the token audience.
- **Public job posts** (`/jobs/[slug]`, `/api/jobs/[slug]/apply`, 2026-10-16): a client's live post and its application form, for anyone with the link. Not part of the client area and not behind any session: `proxy.ts` runs only under `/client` (pinned by `proxy.test.ts`'s matcher test). The only database access is `lib/public/jobs.ts`, on the publishable key with no token (`createUserClient` with a null token, which also refuses a secret key), so every call is `anon`, which may run `job_post_public` and `submit_job_application` and read nothing else (tacit-internal's packages/db, `20261016150000_client_job_posts`). A wrong slug, a draft, a closed post and a post on a job that is not open are the same 404. The page is server-rendered with no script: one input per question named `a_<question id>`, the browser's own `required` / `maxLength` / `type` checks first, and a hidden `website` honeypot the database answers with a quiet success. The form posts to the route, which calls the function and answers with a 303 back to the page carrying a code (`applied=1`, or `error=required|too_long|invalid|busy|failed` and `q=<question id>`), never the database's message; the page owns the wording. What was typed is not kept across an error redirect, which is why the browser checks matter. No resume upload yet: the resume question takes a link. `client-area.test.ts` walks the imports from `app/jobs`, `app/api/jobs` and `lib/public` and fails on a session, a privileged client or a `"use server"` file. The members' side (posting, publishing, the applicants inbox) is apps/mcp's client connector. Since 2026-10-16 the form ends with a **voluntary self-identification** fieldset (US EEO-1 gender and race / ethnicity, veteran and disability status; `EEOC_QUESTIONS` in `lib/public/jobs.ts`), apart from the post's questions, every select defaulting to "I decline to self-identify" and saying the hiring team never sees the answers; the fields are `eeoc_<question>`, passed as `submit_job_application`'s `p_eeoc` and stored with source `candidate` on the new application (tacit-internal's packages/db, `20261016170000_client_reports_eeoc`). Members only ever see an admin's suppressed totals (apps/mcp's `eeoc_report`).

- **Interview notifications to each company's own bot** (2026-10-28): the same machinery tacit-internal runs for Tacit's bot (its `@tacit/core` `notify/`: the Google Calendar sync, the exact five-minute reminder, the check-in after an interview, the cancellation notice), run here once per client company. **The bot** is a row in `agent_destinations` (tacit-internal's packages/db, `20261028120000_notify_per_company`), set by an admin on `/client/integrations` (`integrations/bot.tsx`, `bot-actions.ts`): the four admin-only definer functions on their own token set the https URL (the secret comes back once, as the action's result, shown on the page and never in a URL), rotate the secret, turn it on or off and remove it, each audited. **Verify** (`lib/client/bot.ts`, the second client-area module allowed a privileged client, after reading the row on the admin's own token) sends core's signed `url_verification` challenge; nothing is sent to a bot until it echoes one. **The notifier** is `lib/notify/notifier.ts`, outside the client area, on the service role: `companiesWithBots` (enabled and verified), `companyCalendar` (a member's `calendar_connections` grant with this app's Google client, core's `CalendarDeps.tokenFor`), `companyHub` (the bot as the only channel). `/api/cron/notify` (every two minutes, `vercel.json`, `CRON_SECRET`) runs `runNotifications` with each company's `orgId`; one company failing does not stop the next. `src/workflows/interview-reminder.ts` is the exact T-5 timer (Vercel Workflow; `withWorkflow` in `next.config.ts`; its routes under `/.well-known/workflow/`, outside the proxy's `/client` matcher), re-reading the company's bot when it wakes. `/api/agents/interview-thread` is a bot's thread callback: the Bearer secret names the company. The bot's contract is the `team-bot` docs page. Tests: `api/cron/notify/route.test.ts`, `api/agents/interview-thread/route.test.ts`; the core behaviour is tacit-internal's `per-company.integration.test.ts`.
