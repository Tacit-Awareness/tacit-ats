# @tacit-ats/mcp

Next.js (App Router), one MCP route: `/api/client`, the client connector. Moved here from Tacit-Awareness's `apps/mcp` on 2026-10-16 with its history; that app keeps `/api/mcp` (the iMessage bot) and `/api/connector` (Tacit's own teammates). The caller is a model acting for a client member, which is what most of the design here is about.

## The client connector (`/api/client`)

The MCP server a member of a **client org** adds to Claude: their company's jobs, pipeline and team, the client-facing counterpart of Tacit-Awareness's `/api/connector` (which is Tacit's own teammates, Tacit's org only, on another WorkOS environment). Sign-in, the member's database identity and `whoami` came first (PR 1); the pipeline tools second; the admin tools (jobs, hiring team, access, invitations) third; interviews and feedback fourth.

- **The token exchange.** Supabase trusts WorkOS tokens from the user-management issuer (what the `/client` portal's AuthKit session carries), but an MCP client signs in through AuthKit's OAuth server, whose tokens have the AuthKit domain as issuer. So the route verifies that token itself (`client/oauth.ts`'s `verifyAccessToken`, forked from the staff connector's `connector/auth.ts`: signature against `<CLIENT_MCP_AUTHKIT_DOMAIN>/oauth2/jwks`, issuer, audience = `CLIENT_MCP_RESOURCE_URL`, expiry), then gives the database a token of its own: `@tacit/db`'s `mintClientMemberToken`, 5 minutes, `role: authenticated`, `sub` = the WorkOS user, `org_id` = the WorkOS organization, signed with `SUPABASE_TACIT_SIGNING_KEY`. `current_actor_id()` reads exactly those two claims, so the policies decide as they do for the portal. The minter takes two strings and nothing else, so no caller can put another role or claim in it.
- **Which org.** The token's `org_id` when AuthKit puts one in; otherwise the user's one active WorkOS membership (`client/workos.ts`, needs `CLIENT_WORKOS_API_KEY`); several memberships are refused with "sign in again choosing the company". **Unverified: whether AuthKit's MCP access tokens carry `org_id`.** Both paths are built and tested; the first real sign-in decides which one runs.
- **Who.** `@tacit-ats/core`'s `bindClientActor`, as on the portal: a returning user by subject, a first sign-in by verified email to the actor an admin invited, inside that org. Never creates an actor. Then the database is asked who the member token is (`current_actor_id`, `current_access_level`), and anything but the bound actor is a 403.
- **No other database client.** Tools read and write only through the member's client. `client/bind.ts` (the service role, for binding), `client/audit.ts` (tacit_internal: one `mcp_calls` row per call as `client:<tool>`, and the breadth ceiling's count over the member's own rows) and `client/files.ts` (the service role's Storage, for the `org-files` bucket: `signFileUrl` and `putFile`, called only after the member's own client has read or inserted the `person_files` row, and `removeFiles`, only with the paths `client_anonymize_candidate` returned after deleting those rows) are the only modules under `src/client` allowed a privileged client, each exports only those functions and never a client, and `src/client-connector.test.ts` walks the imports from `src/client` and `app/api/client` and fails otherwise (it also fails if anything else imports the member resolution).
- **Ten pipeline tools** in `client/server.ts`, each one function in `@tacit-ats/core`'s `clientTools` called with `member.db`: reads `whoami`, `list_jobs`, `get_pipeline`, `search_candidates`, `get_candidate`, `list_team` (`readOnlyHint`); writes `add_candidate`, `update_stage` (`destructiveHint`, with `expected_stage` so a move someone else made since is reported, not overwritten), `set_next_action`, `add_note`. What a member sees is what their token reads: an interviewer finds only the people they interview, as a card, and gets no pipeline; an admin sees every job; a hiring-team member the jobs they are on. Output follows the staff connector: a sentence plus the JSON, candidate text (names, headlines, summary, location, note bodies) fenced, ids, stages, emails, links, job titles and teammates bare; a `ClientToolError` comes back as its sentence with `isError`.
- **Nine admin tools** (same file, `@tacit-ats/core`'s `clientTools` admin.ts): `create_job` (admins; open unless told otherwise, on the company's oldest `companies` row, made from the org's name the first time), `update_job` (`destructiveHint`; whoever can manage the job; title, status `open|paused|filled|closed`, location, level, description), `get_hiring_team` (`readOnlyHint`), `add_to_hiring_team` / `remove_from_hiring_team` (admins; team roles `hiring_manager|recruiter|coordinator|sourcer|interviewer`, and the database keeps job access in step with the team), `set_member_access` (`destructiveHint`; admins; through `set_org_member_access`, which never leaves the org without an admin), `invite_member` / `list_invites` / `withdraw_invite` (admins; core's client invite functions, with WorkOS's invitation sent through `client/workos.ts`'s `clientInvitations` over `CLIENT_WORKOS_API_KEY`, naming the member as inviter; without the key `invite_member` refuses and withdrawing skips the WorkOS revoke). Access is spoken as interviewer / hiring team / admin, never the column's limited / elevated / admin. Every one of them is a write the policies already allowed a client admin's token, except `set_member_access`, which needed the function because `authenticated` cannot write `actors`.
- **Five interview tools** (`@tacit-ats/core`'s `clientTools` interviews.ts): `list_my_interviews` (`readOnlyHint`; the caller's own, upcoming / past / all, through `my_interviews()`, since an interviewer's token cannot read the application an interview belongs to), `schedule_interview` (records an interview in Tacit for whoever may schedule on the job, interviewers from the company only, times ISO 8601 with an offset or refused; **no calendar invite is sent to anyone**, unlike the staff connector's Google-backed booking), `update_interview` (`destructiveHint`; move, change interviewers or location, cancel or mark done), `submit_feedback` (the caller's own, on an interview they are on that has started and was not cancelled; filing again replaces theirs) and `get_feedback` (`readOnlyHint`; by interview or application, whatever the org's `feedback_visibility` lets the caller read, with a flag when their own is still outstanding). Feedback notes come back fenced with `private: true`, and are kept out of the `audit_log` row (admins read it).
- **Offers and rejection reasons** (2026-10-14; `@tacit-ats/core`'s `clientTools` offers.ts): `list_rejection_reasons` (`readOnlyHint`; the org's reasons with their kind), `get_offers` (`readOnlyHint`), `create_offer` and `update_offer` (`destructiveHint`), for whoever can manage the job. `update_stage` to rejected or withdrawn now needs `rejection_reason_id` of the matching kind and takes `rejection_note`; on someone already there it replaces the reason. An offer starts as a draft; `update_offer` extends it, records accepted / declined, or withdraws it, and changes a draft's terms. Recording accepted does not mark anyone hired, and nothing is sent to the candidate. `get_candidate` carries each job's rejection reason and note and, for a manager, the latest offer's status. Offer notes and the rejection note come back fenced; terms are bare.
- **Interview plans** (2026-10-15; `@tacit-ats/core`'s `clientTools` plans.ts): `get_interview_plan` (`readOnlyHint`; a job's steps in order and, with `application_id`, that candidate's progress per step: each step's interviews and state, each interviewer's feedback `filed` / `not_filed` / `hidden` by the org's setting, interviews off the plan, the next step; an interviewer sees only their own interviews and the rest reads `not_visible`) and `set_interview_plan` (`destructiveHint`; whoever can manage the job; the whole ordered list replaced, `[]` clears it). The plan is `roles.interview_steps`, the same list the staff connector reads and books against, so there is one plan per job. `schedule_interview` now takes only a step of the plan when the job has one, in the plan's spelling, with a sentence listing the steps otherwise; without a plan any step goes. Interviews on a removed step keep its name, show as off the plan, and `set_interview_plan` says how many. Step names are bare, like job titles: they are passed back verbatim.
- **Files** (2026-10-15; `@tacit-ats/core`'s `clientTools` files.ts, Tacit-Awareness migration `20261015120000_client_person_files`): `list_files` (`readOnlyHint`; a candidate's resumes and attachments the member can read: an interviewer only the resume of someone they interview), `get_file_link` (`readOnlyHint`; the row is read on the member's token, so RLS decides, then `client/files.ts` signs its own `<org_id>/<person_id>/<id>` path for 5 minutes, downloading under the filename; the description says the link expires and that anyone holding it can download until then), `add_file` (whoever can edit the candidate, never an interviewer; kind `resume | attachment`, PDF / Word .doc / .docx / plain text / PNG / JPEG only, the bytes as base64, at most 3 MB decoded because Vercel refuses a request body over 4.5 MB; the filename is letters, digits, spaces and `. _ - ( ) & , + '` with the type's extension; the bytes must start like the type they claim). The row is inserted first, on the member's token with an id made in code and no read-back (the insert policy checks the path is the row's own), then the bytes are uploaded; if the upload fails the member's own client deletes the row again, and the audit claim is given back. `get_candidate` lists the files too. Filenames come back fenced; the filename and bytes stay out of `mcp_calls` and `audit_log`. Without Storage (`CLIENT_FILES_DISABLED` set, or no `files` dep passed to the handler) `get_file_link` and `add_file` refuse in a sentence. Nothing replaces or deletes a file.
- **Files, production setup, once**: the private `org-files` bucket does not exist yet (`20261013120000_client_permissions` left it to "the app PR"; this is that PR) and is not made by a migration, since CI's stack has no storage service. In the Supabase dashboard (Storage > New bucket) or with the service key: name `org-files`, **Public off**, file size limit 3 MB, allowed MIME types `application/pdf, application/msword, application/vnd.openxmlformats-officedocument.wordprocessingml.document, text/plain, image/png, image/jpeg`. Add **no** Storage policies: members never touch the bucket, the service role (`SUPABASE_SECRET_KEY`, already set for `client/bind.ts`) bypasses them. Until it exists, set `CLIENT_FILES_DISABLED=1` on the mcp project, or `add_file` fails with a logged "Bucket not found".
- **Structured scorecards** (2026-10-15; `@tacit-ats/core`'s `clientTools` scorecards.ts): `get_scorecard` (`readOnlyHint`; a job's attributes in order, with `include_archived`; anyone who can see the job, an interviewer included) and `set_scorecard` (`destructiveHint`; whoever can manage the job; the list given becomes the scorecard: matched by name, renamed by `attribute_id`, added, and what is left out archived, never deleted; the same list twice changes nothing). `submit_feedback` takes optional `ratings` (`attribute_id`, `rating` 1-4, `note`), refused before anything is written when an attribute is not live on the interview's job; filing again replaces them. `get_feedback` returns each feedback's `ratings` with the attribute's name. Attribute names are bare like job titles; descriptions and rating notes come back fenced, and rating notes are kept out of the `audit_log` row like feedback notes.
- **Activity, sources and tags** (2026-10-15; `@tacit-ats/core`'s `clientTools` activity.ts and tags.ts): `get_activity` (`readOnlyHint`; one candidate's history newest first: added and how, stage moves with the reason, owner and next-action changes, notes, interviews, offers by status only, tags, each with who did it; whatever the member's token cannot read is simply absent, and an interviewer gets their own notes and interviews rather than a refusal; nulls are left out of each entry), `list_tags` (`readOnlyHint`), `create_tag` (anyone who can add candidates; an existing name is returned, an archived one restored by an admin), `tag_candidate`, `untag_candidate` and `archive_tag` (both `destructiveHint`; admins archive). A tag is named by its `tag_id` or its name, ignoring case. `add_candidate` takes `source` (`sourced`, `suggested`, `applicant`, `referral`, `agency`, `job_board`, `event`, `other`) and `source_detail`, the latter kept out of `mcp_calls` and `audit_log`; `search_candidates` takes `tag`; `get_candidate` carries the tags and each job's source; `get_pipeline` cards carry the source. Tag names, source details and every activity entry's `text` come back fenced; kinds, stages, sources and teammates' names are bare. Interviewers see no tags.
- **Candidate email with templates** (2026-10-16; `@tacit-ats/core`'s `clientTools` email.ts, Tacit-Awareness migration `20261016100000_client_email`): six tools. `list_email_templates` (`readOnlyHint`; not interviewers; with the placeholder list), `create_email_template` and `update_email_template` (admins; the latter `destructiveHint`: rename, rewrite, `archived: true` / `false`; never deleted), `draft_email` (whoever can change the candidate, never an interviewer; a template by name or id, or a subject and body, optionally an `application_id`, which fills `{{job_title}}`; to their address on file or another one on file as `to_email`; sends nothing), `send_email` (`destructiveHint`; the draft's author only, once, at most 30 an hour, enforced in the database) and `list_emails` (`readOnlyHint`; sent ones and your own drafts, with bodies). The server instructions say email is always two steps, the user's explicit yes after seeing the whole draft. Every email is From `CLIENT_EMAIL_FROM` (default `hiring@tacitawareness.com`, a Tacit domain verified in Resend) as `"<member> at <company>"`, with Reply-To the member's own address, through the staff connector's `makeResendSender` (`client/config.ts`'s `clientMailer`). Without `RESEND_API_KEY` drafts are written and `send_email` says sending is not set up; `CLIENT_EMAIL_DISABLED` set turns drafting and sending off (templates still work). A sent email is on the candidate: `get_candidate`'s `emails`, an `email` entry in `get_activity`, and a touch on the application it names. Subjects and bodies come back fenced and are kept out of `mcp_calls` and `audit_log`; addresses, ids and statuses are bare.
- **Approvals** (2026-10-15; `@tacit-ats/core`'s `clientTools` approvals.ts, Tacit-Awareness migration `20261016110000_client_approvals`), six more tools: `get_approval_flow` (`readOnlyHint`; a job's flow of one kind, `offer` or `job_open`, its steps and approvers, and for `job_open` the latest request with its decisions), `set_approval_flow` (`destructiveHint`; whoever manages the job; `steps` is a list of lists of user ids, any one of each inner list approves that step; `[]` removes the flow; a change starts every approval in progress over), `request_approval` (a draft offer by `offer_id` or opening a job by `job_id`; nothing is emailed), `list_my_approvals` (`readOnlyHint`; what waits on the caller's step: the job, and for an offer the candidate, fenced, and the terms), `approve` (optional `comment`) and `reject` (required `reason`), both `destructiveHint`, and the server instructions say to get the user's yes before `set_approval_flow`, `approve` or `reject`. With a flow, `update_offer` cannot extend a draft and `update_job` cannot open a job until the request is approved (the database refuses; the sentence names `request_approval`), changing a draft's terms resets its approval, and a paused job reopens on the approval it already spent. `get_offers` carries each offer's `approval` (required, status, waiting step, decisions with who, when and the reason fenced), `get_activity` carries `approval.requested` / `approved` / `rejected` / `reset` / `cancelled` entries. An approver need not be on the job, an interviewer included: they see only what `list_my_approvals` shows them. Comments and reasons stay out of `mcp_calls` and `audit_log`. No flow: everything behaves as before.
- **Custom fields** (2026-10-16; `@tacit-ats/core`'s `clientTools` custom-fields.ts, Tacit-Awareness migration `20261016120000_client_custom_fields`): `list_custom_fields` (`readOnlyHint`; with `object` and `include_archived`), `create_custom_field` (admins; object `candidate | job | offer`, type `short_text | long_text | number | date | yes_no | single_select | multi_select | url`, `private`, a select field's `options`; a name already there on that object is returned), `update_custom_field` (`destructiveHint`, admins; rename, private, archive / restore, and `options` as the whole live list: `option_id` renames, a name matches or is added, the rest are archived) and `set_custom_field` (`object`, `object_id`, `field` by id or name, `value`: text, number, boolean, date, link, option name or id, a list for multi_select, null clears). A candidate's fields are set by whoever can change the candidate, a job's by whoever manages it, an offer's by whoever manages its job and only while it is a draft; a private field only by admins and the job's managers. `get_candidate`, `list_jobs`, `get_pipeline` and `get_offers` carry `custom_fields` (`field_id`, `field`, `type`, `private`, `value`). Field and option names are bare like job titles; text and url values come back fenced. The value is kept out of `mcp_calls`, and a long_text value out of `audit_log`. Interviewers see no fields.
- **Departments, offices and openings** (2026-10-16; `@tacit-ats/core`'s `clientTools` structure.ts and openings.ts, Tacit-Awareness migration `20261016130000_client_org_structure`): `list_departments` / `list_offices` (`readOnlyHint`; not interviewers), `create_department` (optionally inside a `parent`) / `create_office` (with a `location`), `update_department` / `update_office` (`destructiveHint`; rename, move, archive or bring back; nothing deletes one), all written by admins; each is named by id or name ignoring case. `create_job` takes `department`, `offices` and `openings` (1 unless said), `update_job` takes `department` (null clears) and `offices` (the whole set), and `list_jobs` shows each job's department, offices and opening counts and narrows by `department` (with the departments inside it) or `office`. Openings are Greenhouse's headcount: `list_openings` (`readOnlyHint`; the hiring team and admins, not interviewers or external recruiters), `add_openings` (count, optional codes unique in the company, target start date) and `close_opening` (`destructiveHint`; an open one, with a reason). **Moving someone to hired fills the job's oldest open opening in the database**, and the job becomes filled when the last one fills; moving them out of hired opens it again (and a filled job becomes open, except under a `job_open` approval flow, where reopening the job needs a new approval). `update_stage` to hired says which opening it filled and how many are left. Department and office names and opening codes are bare, like job titles; a close reason and the name of whoever filled an opening are fenced, and the close reason is kept out of `mcp_calls` and `audit_log`.
- **Prospects and talent pools** (2026-10-16; `@tacit-ats/core`'s `clientTools` pools.ts, Tacit-Awareness migration `20261016140000_client_pools`): `add_prospect` (someone with no job yet, for admins and anyone who can add candidates; an email already on file is reused; `source` / `source_detail` like `add_candidate`, the detail kept out of `mcp_calls` and `audit_log`; optional `pool`), `convert_prospect` (puts them in a job at sourced, for whoever has pipeline access to it, carrying the prospect's source unless one is given; confirm first), `list_pools` and `list_pool` (`readOnlyHint`; a pool's people with their pool stage and how many jobs the member sees them in), `create_pool` (anyone who can add candidates; an existing name is returned, an archived one restored by an admin), `archive_pool` (`destructiveHint`, admins), `add_to_pool` (at a stage, `new` by default; with `stage` on someone already there, a move) and `remove_from_pool` (`destructiveHint`). Pool stages are `new`, `contacted`, `engaged`, `not_interested`. `search_candidates` takes `pool` and `prospects_only`; `get_candidate` carries `prospect`, `prospect_source` / `prospect_source_detail` and `pools`. A prospect is read by every member above interviewer who is not an external recruiter and changed by whoever added it and admins (Tacit-Awareness's `packages/db/CLAUDE.md`); interviewers are refused every one of these tools, an external recruiter sees no pools. Pool names and the source detail come back fenced; stages and ids are bare. Seventy-four tools then.
- **Job posts and the applications inbox** (2026-10-16; `@tacit-ats/core`'s `clientTools` posts.ts, Tacit-Awareness migration `20261016150000_client_job_posts`): `list_job_posts` (`readOnlyHint`; a job's or every post the member can see, with status, `accepting_applications`, the public `url`, the form's questions with their `question_id`, and how many applications came in), `create_job_post` (a draft; title defaults to the job's; `questions` built-ins `name`/`email` (always, required) / `phone` / `linkedin` / `resume` (a link) and custom `short_text` / `long_text` / `yes_no` / `select`; left out, the default form is name, email and optional phone, LinkedIn and resume link), `update_job_post` (text and questions in any status; the list replaces the form, a custom question keeps its id when passed again), `set_job_post_status` (`destructiveHint` and in the instructions' confirm-first list; `live` or `closed`, a closed post can go live again, live needs the job open) and `list_applications_inbox` (`readOnlyHint`; job-board applicants still at the first stage with their answers; not for interviewers). Managing posts is for whoever can manage the job. `get_candidate` jobs and `get_pipeline` cards carry `answers` for a job-board application. Answers' values, applicant names, the post a card came through and descriptions come back fenced; question labels, titles and locations are bare, like job titles. Descriptions stay out of `mcp_calls` and `audit_log`. The public page and its form live in apps/web (`/jobs/[slug]`), where an applicant lands in the job at `sourced` with source `job_board`. The link is built from `CLIENT_JOBS_ORIGIN`; neither set, `url` is null. Seventy-nine tools in all (`route.test.ts` pins the list).
- **Duplicates, merging and GDPR erasure** (2026-10-16; `@tacit-ats/core`'s `clientTools` merge.ts, Tacit-Awareness migration `20261016160000_client_merge_anonymize`): all three admins only. `find_duplicates` (`readOnlyHint`; groups of candidates sharing an email ignoring case, a LinkedIn profile or exactly a name, oldest first, with what matched; `candidate_id` narrows to one group), `merge_candidates` (`destructiveHint`; `keep_id`, `merge_id`: everything moves to the record kept -- notes, files, tags, emails, custom field values, pools, interviews, every application -- a job both were in keeps the further-along application and marks the other merged, blank fields are filled, never overwritten, and the duplicate stays on file marked merged and hidden from members; only Tacit can undo it) and `anonymize_candidate` (`destructiveHint`; `confirm` must be `ANONYMIZE <the name on file>`; erases the person and every record merged into them, keeps applications, stages, dates, interviews and ratings as "Anonymized candidate", and then deletes their stored files through `client/files.ts`'s `removeFiles`; irreversible, refused the second time). The server instructions say both writes need the user's explicit yes naming the candidate and are never called unasked, and that nothing deletes a job. `confirm` is kept out of `mcp_calls`; the `audit_log` rows carry ids, counts and column names, and an erasure blanks the before/after of earlier audit rows about that candidate. Files can now be deleted, but only by an erasure. Eighty-two tools in all.
- **Reports and EEO** (2026-10-16; `@tacit-ats/core`'s `clientTools` reports.ts and eeoc.ts, Tacit-Awareness migration `20261016170000_client_reports_eeoc`): `pipeline_report` (`job_id?`, `since?`: per stage now / reached / conversion to next / average days in stage), `source_report` (`since?`), `time_to_hire` (`job_id?`, `since?`: added-to-hired and job-created-to-first-hire, median and average days, jobs listed), `rejection_report` (`since?`: closed per reason and kind), `interviewer_activity` (`since?`: per interviewer, interviews ended, feedback filed on time / late / not filed / not visible; admins and a job's managers only) and `offer_report` (`since?`: by status, acceptance rate, days to an answer), all `readOnlyHint`, computed on the member's own token so each counts only what they can see, refused to interviewers, `truncated` past 5,000 rows. `since` is `YYYY-MM-DD`. **EEO**: `eeoc_report` (`readOnlyHint`; admins only; per answer, applicants and hires, every cell under five shown as `"<5"` and a lone small cell's smallest neighbour `"hidden"`; under five responses no breakdown) and `record_eeoc` (`destructiveHint`; a paper form typed in by whoever manages the job; returns only recorded / replaced; the answers are kept out of `mcp_calls` and `audit_log`). No tool returns one person's EEO answers, `get_candidate` included, and the server instructions say never to guess or infer one. The candidate's own answers come from the public job-post form (apps/web `/jobs/[slug]`, a voluntary section defaulting to decline, through `submit_job_application`'s `p_eeoc`), and erasing a candidate deletes them (Tacit-Awareness's `packages/db/CLAUDE.md`). Every report and `eeoc_report` count live applications only (`merged_into_id is null`, as the policies already hide merged rows), so a merged duplicate is not counted twice; an anonymized candidate still counts, nameless. Reason names, job titles and teammates are bare; no report carries candidate text, so none is fenced and no report counts toward the breadth ceiling. Unit tests in `route.test.ts` (refusals, the call-log args); `client.integration.test.ts` runs each report, a paper form recorded and replaced with nothing in the audit row, a candidate's own answers kept, suppression on real rows, a hiring manager recording but not reporting, and `get_candidate` carrying nothing of it. Ninety tools in all.
- **Read-only connector** (2026-10-15; `@tacit-ats/core`'s `clientTools` connector.ts, Tacit-Awareness migration `20261017110000_client_connector_access`), Greenhouse's read scopes without write scopes: `get_connector_settings` (`readOnlyHint`; any member: `read_write` or `read_only`, who last set it and when) and `set_connector_access` (`destructiveHint`, in the instructions' confirm-first list; admins). **The database enforces it**: in a read-only org `client_claim_write` raises 42501, so every write is refused at its claim before anything is written, and `withAudit` answers with `READ_ONLY_REFUSAL`, a sentence naming the setting, that nothing changed and that an admin can turn it back with `set_connector_access`. Every connector write goes through `withAudit` (checked when this landed: files, email, invitations and erasure included; Storage, Resend and WorkOS are only called inside the claimed write), and the member token is minted here and never leaves, so nothing writes around it. **The way back** is the claim's one exception: an admin's claim for `org.connector_access`, so `set_connector_access` works in read-only mode; an admin can also ask Tacit, who can update `orgs` directly. Decisions: **org-wide only, no per-member override** (access levels already decide what each member can change; a second, per-person switch was not worth explaining until someone asks; it would be a nullable `actors` column read by the same claim). **Write tools stay listed** in read-only mode: clients cache `tools/list` and the setting can change mid-session, so a hidden tool would be stale either way, a missing tool tells the model nothing, and the refusal sentence tells the user why and who to ask; it also keeps `set_connector_access` itself reachable. The `/client` portal is unaffected (it claims nothing), on purpose: the switch is about what a model may do on a member's behalf, not what the member may do.
- **Audit and limits.** Every call is an `mcp_calls` row (`client:<tool>`), and reads are behind the same 150-distinct-candidates-per-hour ceiling as the other two MCP routes (`client/audit.ts`'s `clientBreadthExceeded`, on `tacit_internal`, since the member cannot read `mcp_calls`). Every write is an `audit_log` row claimed on the member's own token through `client_claim_write` before it happens and completed after (Tacit-Awareness's `packages/db/CLAUDE.md`), 300 per member per hour. `source` is `chatgpt` when the User-Agent says so, else `claude`.
- **Answers.** No or bad token, or a token for another audience (the staff connector's included): 401 with a challenge pointing at `/.well-known/oauth-protected-resource/api/client`. ## Conventions specific to this app

- Imports from `src/` are **relative, and without a `.js` suffix**, unlike `packages/*`, which are tsc/NodeNext and need it. The `@/` alias resolves under `next build` but not under vitest; the `.js` suffix builds fine under vitest and tsc but fails `next build`, because Turbopack does not remap `.js` imports to `.ts` files. Do not "fix" either back.
- `mcp-handler` answers `tools/call` over SSE, so the route tests pull the payload out of the `data:` line.
- `vercel.json`'s `buildCommand` builds `@tacit-ats/core` first: types and runtime resolve through its `dist/`, which nothing builds on Vercel unless that file says so. `@tacit/core` and `@tacit/db` arrive built, from `vendor/`.
