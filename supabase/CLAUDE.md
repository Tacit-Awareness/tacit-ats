# supabase/: the client migration track

The schema of the client ATS's own Supabase project, `tacit-ats` (and its staging twin), and the source of truth for it. Split from tacit-internal's `packages/db` on 2026-11-06 (`docs/client-project-split.md`).

## What is here

- `migrations/20261106000000_client_baseline.sql`: the client schema as tacit-internal's 163 migrations left it at `26e0685`, generated by `scripts/client-track/extract-baseline.mjs` (provenance only; never run it again). It is that schema minus the staff-only tables, views and functions in `scripts/client-track/staff-only.json`, which nothing on the client side reaches (worked out from a reference graph over policies, triggers, foreign keys, defaults and function bodies). Some staff tables are still in it, empty, because a client function or trigger names them (`rubrics`, `person_snapshots`, `tacit_submissions`, `enrichment_*`, ...): taking them out means editing those functions, a migration of its own.
  - Privileges are exact: pg_dump writes ACLs relative to Postgres's built-in default, so the baseline ends with `scripts/client-track/acl.sql`'s REVOKE ALL + GRANT for every object (a new project's default privileges would otherwise give `anon` / `authenticated` what tacit revoked).
  - Constraints and indexes are created in the source's oid order: when an insert breaks two unique indexes Postgres reports the lowest oid, and code matches on that name (`interviews_pkey` before `interviews_one_active_per_step`).
  - `scripts/client-track/fingerprint.sql` checked it against tacit object by object: identical apart from ACL order and parentheses in three CHECKs.
- `migrations/20261106010000_staff_bridge.sql`: the bridge's database half (`bridge_client_jobs`, `bridge_job_for_role`, `bridge_submit_candidate`, `bridge_submission_report`, service role only), `roles.staff_role_id`, `people.staff_person_id`, and `orgs.company_id` no longer a foreign key (it names Tacit's CRM row, on tacit).
- `migrations/20261112000000_supabase_auth_groundwork.sql`: groundwork for moving client sign-in from WorkOS to Supabase Auth on this project (plan: https://claude.ai/artifact/DTK4YUVXtJhbCJRq52EEmb). `custom_access_token_hook` adds `org_id` (= `orgs.id`) to every token Supabase issues, from `auth_active_org` (written only by `set_active_org`) or the user's one company; `my_sign_in_orgs()` feeds the company picker; `current_actor_id()` / `current_org_id()` / `current_access_level()` accept either `orgs.workos_org_id` or `orgs.id` as the token's `org_id` until the WorkOS branch is dropped after cutover. A Supabase user's `actors.auth_subject` is their `auth.users` id as text. The local stack registers the hook in `config.toml`; staging and production register it by hand (Authentication → Hooks → Customize Access Token → `public.custom_access_token_hook`) after the migration is pushed.
- `migrations/20261113000000_connector_oauth.sql`: the connector and tats on Supabase Auth's OAuth server (apps/mcp's `CLIENT_AUTH_PROVIDER=supabase`). `choose_connector_company` (the consent page, on the member's token) records the company picked and the authorization's `resource`, reading GoTrue's `auth.oauth_authorizations` by id; `custom_access_token_hook` pins them to the session at the code exchange (`oauth_connector_sessions`) and reads them back on refresh, setting `aud` and `org_id`. The hook never reads GoTrue's tables. `tests/connector_oauth.test.sql`. The local stack's OAuth server is on in `config.toml` (consent at apps/web's `/client/oauth/consent`); hosted: Authentication -> OAuth Server, the same three settings. Locally the connector also needs an asymmetric signing key: `supabase gen signing-key --algorithm ES256`, wrapped in a JSON array, into `supabase/signing_keys.json` (gitignored) and `signing_keys_path` uncommented for that run only, since CI has no such file.
- `scripts/client-track/supabase-cutover.mjs` (2026-11-13): the cutover's relink. A dry run by default (prints the plan, writes nothing); `--apply` finds or creates (`email_confirm`, no password) a Supabase Auth user per address and rewrites each unarchived WorkOS-bound actor's `auth_subject` to it, conditional on the old value; `--send-emails` then sends each relinked address the reset email (recovery template, to set a password); `--rollback <file>` puts back what a run recorded in its `cutover-<time>.json` (written before the first change and after each). Pending invitations, Supabase-bound and archived actors are left alone; an address with two WorkOS subjects, or an actor with no email, is reported and skipped. Needs `SUPABASE_URL` and `SUPABASE_SECRET_KEY`. Tested on the local stack (dry run, apply, a new account, mixed-case email, the skips, rollback); a production dry run on 2026-11-13 planned 13 actors across 5 addresses with no skips.
- `tests/*.test.sql`: plain SQL, each one transaction rolled back, raising on the first failure. Five came from tacit-internal at the split (`org_tenancy` minus its staff-only checks), plus `bridge.test.sql`.
- `config.toml`: the local stack, project_id `tacit-ats`, ports 557xx so it runs beside tacit-internal's (543xx).

## Rules

- **New client schema lands here**, not in tacit-internal. `supabase migration new <name>`, a timestamp after everything on main (CI's `check-migration-order.sh`). tacit-internal's `packages/db` still owns the staff project; its client tables there are frozen and go away after the cutover.
- **Merging pushes.** CI's `migrate-staging` then `migrate-production` run `supabase db push` for each GitHub environment that has `SUPABASE_PROJECT_REF` (and `SUPABASE_DB_PASSWORD`, plus the repo's `SUPABASE_ACCESS_TOKEN`). Until those exist they skip. Additive migrations only while apps on the old schema still run.
- **Types**: the apps are still typed by the vendored `@tacit/db`, which this schema is a superset of for every client table. A function or column only this track has is typed where it is called (`apps/web/src/lib/bridge/requests.ts`'s `BridgeCall`). Generating this track's own types and retiring `@tacit/db`'s is a follow-up.
- Roles are per cluster: `tacit_internal` is created idempotently at the top of the baseline. The `org-files` and `org-brand` buckets are made by hand (or by `copy-orgs.mjs --storage`) once per project.

## Commands (repo root)

```
supabase start            # Docker; first run pulls images
supabase db reset         # replay the track
for f in supabase/tests/*.sql; do psql "$(supabase status -o env | sed -n 's/^DB_URL="\(.*\)"$/\1/p')" -v ON_ERROR_STOP=1 -q -f "$f"; done
pnpm test:integration     # the whole client suite against this stack
```
